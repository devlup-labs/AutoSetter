# PHASE 3 — GENERATE HEAVIER VALID ALTERNATIVES

Construct candidate approaches that preserve correctness while intentionally adding unnecessary computational or structural complexity.

Prefer transformations such as:

* `O(N)` → `O(N log N)` using Segment Tree, Fenwick Tree, ordered structure, balanced tree, or repeated binary search.
* Direct array access → range-query data structure.
* Simple prefix computation → Fenwick Tree or Segment Tree.
* Basic BFS on an unweighted graph → Dijkstra's algorithm with a priority queue.
* Direct arithmetic → binary search over an answer with a monotonic validity predicate.
* Simple membership checks → ordered set or map where hashing or direct indexing would suffice.
* Straightforward aggregation → coordinate compression plus tree-based queries.
* Simple graph traversal → more general shortest-path machinery when mathematically equivalent.
* Direct counting → data structure maintenance with logarithmic updates.
* Single-pass computation → multiple structured passes when correctness remains unchanged.
* Simple state transition → a more general framework such as a graph or DP representation when valid.

The selected approach must satisfy:

HEAVY_APPROACH_CORRECTNESS = true

and:

RESULT(HEAVY_APPROACH) = RESULT(BASELINE_APPROACH)

for every valid input.

The approach may introduce:

* Higher asymptotic complexity.
* Larger constant factors.
* More complex data structures.
* Extra logarithmic factors.
* Redundant but valid computation.

The approach must not introduce:

* Incorrect answers.
* Undefined behavior.
* Invalid assumptions.
* Randomized correctness failures.
* Dependence on unspecified input properties.
* Numerical errors that violate problem requirements.

# PHASE 4 — HEAVY APPROACH SELECTION ALGORITHM

Evaluate candidate approaches using the following decision rules.

For each candidate:

A. Correctness Check

* Does the candidate produce the exact required result for all valid inputs?

B. Specification Compatibility Check

* Does it respect all input constraints?
* Does it support all required edge cases?
* Does it preserve required ordering or output semantics?

C. Over-Engineering Check

* Is it structurally or computationally heavier than the likely baseline?
* Does it use additional machinery that is unnecessary but valid?

D. Complexity Check

* Is the algorithm finite and implementable under C++17?
* Does its complexity remain mathematically meaningful for the stated constraints?
* It may be slow or potentially TLE, but it must not be logically impossible to execute.

Select a candidate satisfying:

CORRECTNESS = PASS
SPECIFICATION_COMPATIBILITY = PASS
OVER_ENGINEERING = PASS

Prefer the candidate with the following characteristics, in order:

1. Exact correctness.
2. Clear unnecessary sophistication.
3. General-purpose data structures or algorithms.
4. Extra logarithmic overhead where possible.
5. Larger but understandable implementation complexity.
6. Reliable implementation under C++17.

Do not sacrifice correctness merely to make the implementation heavier.
