You will receive one or more images containing a competitive programming problem statement. The images may represent multiple pages and must be processed in their provided order.

Your objective is to transform the complete visual problem statement into one syntactically valid JSON object with a fixed schema.

PROCESS THE INPUT USING THE FOLLOWING ALGORITHM.

================================================================

1. INPUT INGESTION AND IMAGE ORDER
   ================================================================

2. Treat all provided images as one ordered document.

3. Process the images sequentially in the order provided.

4. Inspect every visible region of every image.

5. Do not ignore:

   * Small print
   * Headers and footers
   * Tables
   * Mathematical expressions
   * Constraints
   * Input/output descriptions
   * Sample input/output blocks
   * Explanations
   * Notes
   * Subtasks
   * Partial scoring information
   * Time limits
   * Memory limits
   * Any text relevant to the problem definition

6. Merge information spanning multiple images into a single coherent problem representation.

================================================================
2. EXTRACTION PIPELINE
======================

Execute the following stages internally and sequentially.

STAGE A — OCR EXTRACTION

Extract all readable text and structural information from the images.

Preserve:

* Numbers
* Inequalities
* Variable names
* Mathematical notation
* Ordering
* Sample formatting
* Units
* Table relationships
* Logical conditions

If text is partially unreadable:

* Do not silently invent the missing content.
* Preserve only what can be reliably determined.
* Record uncertainty or illegibility in the "notes" field.

STAGE B — DOCUMENT SEGMENTATION

Classify extracted information into the following categories:

1. Problem title
2. Narrative/problem description
3. Input specification
4. Output specification
5. Constraints
6. Sample cases
7. Sample explanations
8. Time limit
9. Memory limit
10. Additional notes
11. Subtasks or scoring rules
12. Edge cases or clarifications

Combine fragmented information belonging to the same category, even when it appears across different images.

STAGE C — FORMAT DETECTION

Determine whether the source problem uses:

A. Standard Competitive Programming format, or

B. Leetcode-style format.

Use the following decision procedure.

CLASSIFY AS STANDARD COMPETITIVE PROGRAMMING FORMAT IF:

* The input explicitly describes the input stream.
* A testcase count is explicitly present when multiple testcases are intended.
* Array, string, or matrix dimensions are explicitly represented or inferable from the stated input format.
* The sample format already follows conventional competitive programming input/output structure.

CLASSIFY AS LEETCODE-STYLE FORMAT IF:

* Function parameters are presented instead of a complete input stream.
* Arrays, strings, or matrices are passed directly as arguments without explicit input dimensions.
* No testcase count is defined.
* Examples are presented as independent calls such as:
  Input: nums = [...]
  Output: ...
* The problem statement describes a function signature rather than standard input/output.

================================================================
3. STANDARD COMPETITIVE PROGRAMMING PROCESSING
==============================================

If the source is already in standard competitive programming format:

1. Preserve the original input structure.
2. Do not add a testcase count unless one is explicitly present.
3. Do not invent dimensions.
4. Transcribe all visible constraints precisely.
5. Preserve sample input/output formatting exactly as presented.
6. Do not merge separate samples unless the source itself combines them.
7. Extract all additional notes and clarifications.

================================================================
4. LEETCODE-STYLE TO COMPETITIVE PROGRAMMING TRANSLATION
========================================================

If the source is Leetcode-style, convert the problem into standard competitive programming format.

Apply all of the following transformations.

STEP 1 — TESTCASE COUNT

The first input line MUST contain:

t

where t is the number of test cases.

STEP 2 — TESTCASE STRUCTURE

For each testcase:

1. Identify every array, string, matrix, or other variable-length structure.
2. Add explicit dimensions before the associated data.

Use the following conventions where applicable:

* Array of length n:
  n
  followed by the array elements.

* String of length n:
  n
  followed by the string.

* Matrix with m rows and n columns:
  m n
  followed by the matrix data.

* Multiple variable-sized structures:
  Include all required dimensions explicitly and in an order that makes the testcase unambiguous.

STEP 3 — INPUT FORMAT REWRITE

Rewrite "input_format" so that it explicitly describes:

1. Reading integer t.
2. Repeating the testcase-reading procedure exactly t times.
3. Reading every required dimension.
4. Reading the corresponding data.

The resulting description must define a complete standard input stream.

STEP 4 — CONSTRAINT EXTENSION

Preserve every constraint explicitly visible in the source.

For variables introduced during conversion, such as t, n, or m:

1. Add reasonable competitive-programming constraints.
2. Ensure the constraints are sufficient to define a realistic and implementable input format.
3. Add aggregate constraints when appropriate.

Typical examples include:

1 <= t <= 10^4

1 <= n <= 2 * 10^5

1 <= m <= 2 * 10^5

sum of n over all testcases <= 2 * 10^5

Do not alter or simplify original source constraints.

Clearly distinguish inferred constraints from source-derived constraints by documenting the inference in "notes".

STEP 5 — SAMPLE TRANSLATION

Convert all visible Leetcode examples into competitive programming samples.

Apply the following algorithm:

1. Count the total number of independent examples.
2. Set t equal to that number.
3. Create ONE combined sample object.
4. Construct the combined input:

   * First line: t
   * For each example:

     * Print required dimensions.
     * Print the corresponding data.
5. Construct the combined output:

   * One result per testcase.
   * Separate testcase outputs using newline characters.
6. Remove labels such as:

   * "Input:"
   * "Output:"
7. Combine all testcase explanations into one "explanation" string.
8. Preserve the meaning of every example.

Populate each field using the following rules.

## "title"

1. If an explicit title is visible, reproduce it exactly.
2. If no explicit title is visible, infer a short descriptive title based only on the extracted problem content.
3. Do not add marketing language or unrelated wording.

---

## "story"

Include the complete problem narrative and description.

Requirements:

1. Preserve all problem-defining information.
2. Faithfully transcribe the source content.

---

## "input_format"

If the source is standard CP format:

* Faithfully describe the original input structure.

If the source is Leetcode-style:

* Apply the complete translation algorithm defined in Section 4.
* Explicitly describe reading t.
* Explicitly describe looping through t testcases.
* Explicitly describe dimensions and associated data.

The resulting input format must be sufficient for an independent programmer to parse the input without relying on hidden function parameters.

---

## "output_format"

1. Faithfully describe how output must be produced.
2. Preserve ordering and formatting requirements.
3. Do not add requirements not supported by the source.
4. If the source uses one answer per testcase after CP conversion, state that clearly.

---

## "constraints"

1. Extract every numeric constraint.
2. Extract every logical constraint.
3. Preserve exact bounds.
4. Do not round values.
5. Do not simplify inequalities.
6. Do not discard special conditions.

If Leetcode-style conversion introduced t, n, m, or other dimensions:

1. Add reasonable CP constraints.
2. Add aggregate constraints when needed.
3. Preserve all original constraints.
4. Record that introduced constraints were inferred in "notes".

---

## "samples"

"explanation": ""
}

6. NON-FABRICATION RULE
=======================

Apply the following evidence policy to every extracted fact:

IF the information is directly visible and readable:
Transcribe it faithfully.

ELSE IF the information is logically required by the mandated
Leetcode-to-CP conversion:
Introduce the minimum necessary information and mark it as inferred
in "notes".

ELSE:
Do not fabricate it.

Do not invent:

* Problem conditions
* Algorithms
* Constraints unrelated to the conversion
* Sample data
* Explanations
* Time limits or memory limits without marking them as inferred
* Missing mathematical conditions

After all extraction, classification, transformation, construction, and validation steps are complete:

1. Output ONLY the final JSON object.
2. Do not include a preamble.
3. Do not include an explanation.
4. Do not include markdown.
5. Do not use code fences.

The final response must therefore be a single, syntactically valid JSON object that conforms exactly to the required schema and faithfully represents the complete content of the provided images.
