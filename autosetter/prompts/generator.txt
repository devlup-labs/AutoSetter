# PHASE 2 — BUILD THE Z3 VARIABLE MODEL

For each extracted input variable, determine the appropriate Z3 sort and define the corresponding Z3 variable.

Apply the following decision rules.

## Rule A — Integer variables with bounded domains

For integer variables whose domain fits comfortably within standard integer range:

Use `z3.Int(name)`.

Examples:

* Array sizes.
* Counts.
* Indices.
* Small numeric values.
* Coordinates.

## Rule B — Large integer variables

For integer variables whose domain requires 64-bit values or whose constraints involve large products or sums:

Use `z3.Int(name)`.

Z3 Int handles arbitrary precision. Do not use BitVec for general integer constraints unless the problem specifically involves bitwise operations.

## Rule C — Boolean variables

For variables that are binary flags or boolean choices:

Use `z3.Bool(name)`.

## Rule D — BitVec variables

For variables that involve bitwise operations, masks, or XOR constraints:

Use `z3.BitVec(name, bit_width)`.

Select bit width based on the maximum domain value.

## Rule E — Array and collection variables

For arrays or sequences of N elements:

Define individual Z3 variables for each element:

```
a = [z3.Int(f"a_{i}") for i in range(max_n)]
```

where `max_n` is the maximum possible array length.

When the array length itself is a Z3 variable, define enough element variables for the maximum possible length, and constrain only the first N elements.

## Rule F — String variables

For string variables:

Model each character as a separate Z3 Int constrained to the valid character range.

For example, for a lowercase string of length up to L:

```
s = [z3.Int(f"s_{i}") for i in range(max_len)]
```

Constrain each character: `ord('a') <= s[i] <= ord('z')`.

## Rule G — Graph edge variables

For graph problems requiring M edges between N nodes:

Define edge endpoint pairs:

```
u = [z3.Int(f"u_{i}") for i in range(max_m)]
v = [z3.Int(f"v_{i}") for i in range(max_m)]
```

## Naming Convention

All Z3 variable names must be descriptive and correspond to the variable names used in the JSON specification.

Use the exact names from `input_format` when possible.

# PHASE 3 — ENCODE DOMAIN BOUNDS

For every Z3 variable defined in Phase 2, add explicit lower and upper bound constraints.

This phase is mandatory. No Z3 variable may remain unbounded.

Apply the following rules.

## Rule A — Scalar bounds

For each scalar variable with bounds [L, U]:

```
solver.add(var >= L)
solver.add(var <= U)
```

Or equivalently using `z3.And`:

```
solver.add(z3.And(var >= L, var <= U))
```

## Rule B — Dependent bounds

When a variable's bounds depend on another variable:

Express the dependency explicitly.

Example: Array element a[i] must satisfy 1 ≤ a[i] ≤ N:

```
for i in range(max_n):
    solver.add(z3.Implies(i < n, z3.And(a[i] >= 1, a[i] <= n)))
```

where `n` is the Z3 variable representing the array length.

## Rule C — Collection length bounds

For collection sizes:

```
solver.add(z3.And(n >= MIN_N, n <= MAX_N))
```

## Rule D — Graph edge bounds

For graph edge endpoints:

```
for i in range(max_m):
    solver.add(z3.Implies(i < m, z3.And(u[i] >= 1, u[i] <= n)))
    solver.add(z3.Implies(i < m, z3.And(v[i] >= 1, v[i] <= n)))
```

## Verification requirement

After completing this phase, every Z3 variable must have at least one lower bound constraint and one upper bound constraint, either directly or through an implication guarded by a size variable.

# PHASE 4 — ENCODE STRUCTURAL VALIDITY CONSTRAINTS

Translate every structural constraint from the JSON into Z3 expressions.

These are constraints that define what makes an input valid, independent of adversarial considerations.

## Category A — Distinctness

When the specification requires distinct elements:

Prefer `z3.Distinct()`:

```
solver.add(z3.Distinct([a[i] for i in range(fixed_n)]))
```

When the array length is a Z3 variable, apply distinctness conditionally or use pairwise inequality within the valid range.

## Category B — Ordering

When sorted, strictly increasing, non-decreasing, or other orderings are required:

```
for i in range(max_n - 1):
    solver.add(z3.Implies(i + 1 < n, a[i] < a[i + 1]))  # strictly increasing
```

## Category C — Permutations

When the input must be a permutation of 1..N:

```
solver.add(z3.Distinct([a[i] for i in range(fixed_n)]))
for i in range(fixed_n):
    solver.add(z3.And(a[i] >= 1, a[i] <= fixed_n))
```

## Category D — Graph validity

For simple graphs (no self-loops, no multi-edges):

```
for i in range(max_m):
    solver.add(z3.Implies(i < m, u[i] != v[i]))  # no self-loops
```

For distinct edges, add pairwise inequality on edge pairs.

## Category E — Tree constraints

For tree inputs (N nodes, N-1 edges, connected):

Trees are difficult to express purely in Z3. Consider:

1. Define edges and enforce N-1 edge count.
2. Use Z3 for node labels and edge endpoints.
3. Use a post-solve construction step to build a valid tree structure using `random` seeded by the command-line seed.

When Z3-only tree generation is impractical, use a hybrid approach: generate N and node properties via Z3, then construct the tree topology programmatically using Prüfer sequences or random parent assignment.

## Category F — String constraints

For string character sets:

```
for i in range(max_len):
    solver.add(z3.Implies(i < length, z3.And(s[i] >= ord('a'), s[i] <= ord('z'))))
```

## Category G — Sum and aggregate constraints

When the problem specifies sum constraints (e.g., sum of all N across test cases ≤ S):

```
solver.add(z3.Sum([n_tc[i] for i in range(t)]) <= S)
```

## Category H — Index validity

When variables represent indices into other structures:

```
solver.add(z3.And(idx >= 1, idx <= n))
```

Do not silently omit any structural constraint explicitly present in the JSON.

Translate every relational constraint that involves relationships between two or more variables.

These include:

For each relational constraint explicitly present in or derivable from the JSON:

1. Identify the participating variables.
2. Express the relationship as a Z3 expression.
3. Add it to the solver.

Do not silently omit relational constraints.

# PHASE 6 — SEED-BASED DIVERSIFICATION

The generated script must produce different valid test cases when invoked with different seeds.

Implement the following diversification mechanism.

## Step 1 — Accept the seed from command line

```
seed = int(sys.argv[1])
```

## Step 2 — Configure Z3 solver randomization

```
z3.set_param('smt.random_seed', seed)
```

This causes Z3 to explore different satisfying assignments for different seeds.

## Step 3 — Optional Python randomization

When post-solve shuffling, permutation, or random construction is needed:

```
import random
random.seed(seed)
```

Use Python's `random` module only for:

* Shuffling arrays after Z3 produces a valid set of values (when ordering is not constrained).
* Constructing tree topologies or graph structures after Z3 produces valid node/edge properties.
* Selecting among multiple valid configurations.

Do not use `random` to generate values that should be constrained by Z3.

## Step 4 — Soft constraint variation (optional, advanced)

When appropriate, add soft constraints or optimization objectives that vary with the seed to encourage diverse test coverage:

* Even seeds may target larger values of N.
* Odd seeds may target boundary values.
* Specific seed ranges may target specific adversarial properties.

This is optional and should only be used when the problem structure benefits from it.

# PHASE 7 — ADVERSARIAL PROPERTY IDENTIFICATION

Before finalizing the constraint model, systematically identify adversarial test properties that random generation would be unlikely to discover.

Perform the following analysis internally.

## Step 1 — Boundary analysis

Identify constraints that should be tested at their exact boundaries:

* Maximum N, M, or other size parameters.
* Minimum valid inputs (N=1, empty arrays when allowed).
* Values at the exact upper or lower bound.
* Values of zero when zero is at the domain boundary.

## Step 2 — Structural edge cases

Identify structural configurations that stress-test solutions:

* All elements equal.
* All elements at maximum value.
* All elements at minimum value.
* Strictly increasing sequence.
* Strictly decreasing sequence.
* Alternating pattern.
* Single large component with many small components (for graphs).
* Star graph, path graph, complete graph (for graph problems).
* Long chains (for tree problems).

## Step 3 — Algorithmic stress cases

Identify inputs that target common algorithmic weaknesses:

* Inputs that cause worst-case behavior for naive sorting.
* Inputs that cause maximum recursion depth.
* Inputs that trigger integer overflow in intermediate computations.
* Inputs that stress hash collision behavior.
* Inputs where the greedy choice is ambiguous.
* Inputs where the optimal answer lies at a boundary.

## Step 4 — Select adversarial strategy

Based on the seed value, select which adversarial property to target:

* Low seeds (1-3): boundary cases.
* Mid seeds (4-7): structural stress cases.
* Higher seeds (8+): diverse random cases.

This selection should be encoded as conditional constraints or post-solve construction choices.

Not all adversarial properties apply to every problem. Select only those relevant to the problem's structure.

# PHASE 8 — SOLVER CONFIGURATION AND EXECUTION

Configure and execute the Z3 solver with appropriate settings.

## Step 1 — Create the solver

```
solver = z3.Solver()
```

## Step 2 — Set resource limits

```
solver.set('timeout', 30000)  # 30 seconds maximum
```

## Step 3 — Add all constraints

Add all constraints from Phases 3, 4, 5, 6, and 7 to the solver.

## Step 4 — Check satisfiability

```
result = solver.check()
```

## Step 5 — Handle results explicitly

```
if result == z3.sat:
    model = solver.model()
    # proceed to extraction
elif result == z3.unsat:
    print("UNSAT: constraints are contradictory", file=sys.stderr)
    sys.exit(1)
else:
    print(f"UNKNOWN: solver returned {result}", file=sys.stderr)
    sys.exit(1)
```

Never silently ignore an UNSAT or UNKNOWN result.

Never proceed to output without a confirmed satisfying model.

# PHASE 12 — PERFORMANCE CONSTRAINTS

The generated script must be efficient enough to run in a test-generation pipeline.

Adhere to the following performance rules.

## Rule A — Avoid nonlinear integer arithmetic

Do not create constraints involving multiplication of two Z3 variables when avoidable.

Nonlinear arithmetic (e.g., `x * y == z` where both x and y are Z3 variables) is much slower to solve.

When multiplication is needed, prefer:

* Fixing one factor and constraining the other.
* Using `z3.If()` with bounded choices.
* Pre-computing products outside Z3.

## Rule B — Prefer built-in Z3 constraints

Use `z3.Distinct()` instead of pairwise inequality.

Use `z3.Sum()` instead of manual accumulation.

Use `z3.If()` for conditional expressions.

Use `z3.And()`, `z3.Or()`, `z3.Not()` for logical combinations.

## Rule C — Bound all variables

Every Z3 variable must have finite bounds. Unbounded variables cause the solver to explore unnecessarily large search spaces.

## Rule D — Minimize variable count

Do not define Z3 variables for values that can be derived from other variables after solving.

If a value is deterministically computable from the model, compute it in Python rather than adding it as a Z3 variable.

## Rule E — Use solver timeout

Always set a solver timeout to prevent unbounded execution:

```
solver.set('timeout', 30000)
```

## Rule F — Prefer simple constraint forms

Express constraints in the simplest algebraically equivalent form.

Avoid deeply nested or redundant constraint expressions.
