AutoSetter: from a statement screenshot to a Polygon package

By IamShreshth, project overview, October 2026

Hello, Codeforces-style readers!

Anyone who has set a problem knows the statement is the easy part. After it come the validator, the checker, a main solution, some wrong solutions that must fail, tests that reach the limits, and finally uploading it all to Polygon by hand.

AutoSetter is our attempt to automate that. You give it a picture or PDF of a problem statement, and it gives back a complete Polygon package:

  • problem.json: the statement read into a structured spec (title, story, input/output format, constraints, samples, limits)
  • a statement, a C++17 main solution, plus greedy, brute-force and heavy solutions
  • a testlib validator.cpp and checker.cpp
  • tests generated with Z3 from a declarative spec, including max-size cases
  • a validation report and a manifest.json saying whether the package is fit to release

Before generating anything, it checks a vector database of existing problems. If the problem already exists, you get the link and no package. Otherwise it can push the package to Polygon with your API key.

This page explains how the project works inside. It is not a product page.

Three checks against "the model agrees with itself"

By Aeshvarya Awasthi, validation design

When one model writes the validator, the solution and the checker from the same JSON, all three can share the same mistake and still pass each other. So the pipeline never trusts a file because another generated file agrees with it:

  1. Official samples check the validator. The samples in the statement are known-good input, so a correct validator must accept all of them. If it rejects one, the validator (or the extracted constraints) is wrong.
  2. The validator checks the generator. If the validator accepts the samples but rejects a generated test, the generator is the file at fault.
  3. Wrong outputs probe the checker. Running the checker on the solution's own output only shows that x == x. So we also feed it outputs we know are wrong:
  ✅ checker rejected: an empty output file
  ✅ checker rejected: a correct answer with its last token missing
  ✅ checker rejected: a correct answer with an extra token appended
  ✅ checker rejected: a correct answer with every number increased by one

When a check fails, only the files at fault are regenerated, with the exact error as feedback, for up to three rounds.

Z3 instead of a hand-written generator

By Aeshvarya Awasthi & YajatGupta07, test generation

Models write random generators that often break the constraints, for example k > n or a sum(n) over the limit. So instead the model writes a declarative spec of the input:

{ "vars": { "n": [1, 200000], "k": [1, "n"] },
  "arrays": { "a": { "len": "n", "range": [1, 1000000000] } },
  "file_constraints": ["sum(n) <= 200000"], ... }
  • Z3 solves the integers. Each integer is a variable with its bounds and constraints, fixed one at a time inside the range Z3 says is still feasible.
  • Builders fill the bulk. Arrays, strings, trees and graphs are built directly, so an n = 2·105 test takes about a second.
  • Each seed has a strategy: 1 = all minimum, 2 = all maximum, then random, small, near-max, log-scaled, with matching shapes (sorted arrays, path/star trees).
  • The spec must parse the official samples. If it can't, it goes back to the model like a compile error.

Is this problem already on Codeforces?

By swasti_singhal & IamShreshth, vector database

vector_database/ collects Codeforces and LeetCode problems, normalizes and deduplicates them, embeds them with BAAI/bge-small-en-v1.5 (384 dimensions), and stores them in Qdrant with cosine distance.

At run time, the extracted problem.json is embedded the same way, and we take only its single nearest neighbour (k = 1). If the cosine similarity is above 0.80, we print the link and stop.

Results from a real run against our 12-problem test collection:

QueryNearest stored problemCosineVerdict
Theatre Square, reworded1A Theatre Square0.9517Exists
Watermelon, reworded4A Watermelon0.9485Exists
Two Sum (not stored)489C Given Length and Sum of Digits0.8017False positive

The last row is a known issue. This embedding model rates even unrelated problems around 0.75–0.80, while real copies score about 0.95, so a 0.80 threshold sits in the noise. It is configurable (--similarity-threshold), and around 0.90 looks safer.

One command, straight to Polygon

By IamShreshth, CLI & Polygon API

The CLI asks for your Polygon API key and secret first and verifies them, so a long run never stops at the end to wait for input. Once the package passes validation, it creates the problem and uploads everything.
